## API ownership follow-up, stacked on the Docker pilot

The `fix/api-user-ownership` branch is a separate security change based on `chore/docker-local-pilot` (#224). Backend routes now verify Supabase bearer tokens before user-owned writes and private notification reads, derive owner IDs from verified users, and return only safe profile fields on public reads. The frontend sends its current session token for these calls. Local negative tests assert that missing, invalid, and cross-user requests are denied before privileged DB or Storage writes; focused tests cover valid owner flows and rapid bookmark/follow toggles. The exact committed-image container result and image identity are recorded in the stacked PR.

These local fixtures do not prove actual Supabase Auth, RLS, Storage ownership, multi-user separation, or durable persistence. U2-U4 provider-backed acceptance remains **BLOCKED** until a disposable isolated Supabase project is available. The fixture-only `auth-container-smoke.mjs` uses loopback services and a fixed disposable account; it never contacts production or reads production credentials.

## AWS API and weekly worker readiness

The fork's AWS Compose boundary keeps the API on host loopback port 3003 and the Playwright worker private. The worker writes a fixed-schema status document to its dedicated named volume by replacing a temporary file atomically. On restart, an unfinished run becomes `interrupted`; a completed run is `fresh` for eight days, then `stale`. `scrapeReady` requires both restaurant and menu success. The worker health check reports process/scheduler failure separately from weekly completion. The API `/ready` remains only a restaurants query. The stdout operational feed contains only reviewed fixed-message JSON records; raw diagnostics stay on stderr and must remain outside the dashboard feed.
