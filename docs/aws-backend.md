# UMami AWS backend preparation

The Vercel frontend uses `https://umami.elischiffler.dev`. Set its Production `VITE_API_BASE_URL` to `https://api.umami.elischiffler.dev` and redeploy after the API is reachable. The API allows the frontend origin in CORS. The API and scraper worker are separate containers; the worker has no published port.

`compose.aws.yaml` binds the API only to the host loopback address at port 3003. Route `api.umami.elischiffler.dev` through the shared server's HTTPS reverse proxy to `127.0.0.1:3003`, and set that subdomain's DNS to the instance's public address after production acceptance. This PR does not configure the reverse proxy or DNS. Do not publish port 3003 directly to the Internet.

On the instance, create `backend/.env.production` outside version control with restrictive filesystem permissions. It must contain `SUPABASE_URL` and `SUPABASE_SECRET_KEY` for the approved managed Supabase project. The worker also needs outbound access to its allowlisted HTTPS sources `apiv4.dineoncampus.com` and `www.subway.com`. Never place these values in the Vercel frontend variables or images. The Compose file enables live scraping, so only start it when those destinations are approved. Runtime names: `SUPABASE_URL`, `SUPABASE_SECRET_KEY`, `CORS_ORIGINS`, `PORT`, `UMAMI_SCRAPER_MODE`, `UMAMI_ALLOW_LIVE_SCRAPES`, `WORKER_PORT`, `WORKER_STATE_PATH`, and `TZ`; `UMAMI_REVISION` and `UMAMI_API_PORT` are Compose inputs. `VITE_API_BASE_URL` is a frontend build variable, not a backend secret.

Deploy only a merged, checked `main` commit. Set `UMAMI_REVISION` to its full SHA, then run `docker compose -f compose.aws.yaml config --quiet`, `docker compose -f compose.aws.yaml build`, and `docker compose -f compose.aws.yaml up --detach --wait`. Verify `/ready`, a CORS preflight from the frontend origin, the reverse proxy's TLS endpoint, and the worker health before directing the Vercel frontend at this API. Deployments to this Compose project must run serially; retain the prior image tag for rollback. Do not run `down --volumes` as part of deployment.

Restaurants run Monday at 08:00 and menus Tuesday at 08:00, both in `America/Los_Angeles`. The private worker `/health` reports process health and becomes unhealthy after a failed or interrupted tracked run. `/status` also reports each job as `missing`, `running`, `fresh`, `stale`, `failed`, or `interrupted`; `scrapeReady` is true only after both jobs completed successfully within eight days. Scheduler activity alone does not prove a completed scrape. A fresh worker starts with missing jobs until a run occurs. The fixed-schema status file is atomically replaced on the dedicated `worker-state` volume and contains only job names, timestamps, and status, with no provider error text. A run left in progress across restart is marked interrupted. Do not delete this volume on deploy or rollback. A failed job needs diagnosis and a successful rerun to recover.

The API `/ready` proves only a minimal restaurants query using the configured server key. Before routing production traffic, separately verify a production-origin `OPTIONS /api/restaurants` preflight with `Access-Control-Request-Method: GET` and confirm `Access-Control-Allow-Origin: https://umami.elischiffler.dev`; then verify an authenticated business route, two-user ownership and RLS, Storage object bytes, scraper writes and idempotence on an explicitly approved isolated Supabase project. These gates remain blocked without approved provider resources and secrets. The worker status file is a scheduler signal, not evidence of Auth, RLS, Storage, or database restore.

API and worker stdout emit only fixed-message JSON records with ISO 8601 `timestamp`, `level`, and `message`. Legacy diagnostic console output goes to stderr and stays private. The host operator may filter and atomically rotate only reviewed stdout records into read-only `/var/lib/hosting-ops/logs/umami-api.jsonl` and `umami-worker.jsonl`; do not feed raw Docker logs or stderr to the dashboard. The host owns collection, file permissions, retention and read-only mounting. Docker json-file logs rotate at 10 MiB times three files per container.

Supabase owns database, Auth, and Storage persistence. Before release, record separate database and Storage-byte backups, Auth recovery ownership, and an isolated restore drill; [Supabase database backups do not contain Storage objects](https://supabase.com/docs/guides/platform/backups). Preserve the prior full-SHA API and worker images for rollback. A container rollback does not reverse database migrations or restore deleted provider data. Sequence incompatible schema changes separately with a recovery plan before merge.

The API container is limited to 256 MiB and the Playwright worker to 1 GiB, plus 256 MiB of shared memory. The instance needs headroom for Docker, the reverse proxy, and any other projects. Do not use the smallest 1 GiB instance for the complete shared stack. This file does not provision AWS, the reverse proxy, DNS, Supabase resources, or production secrets.
